Enrichissement CTI — Chaque Étape

Le pipeline d'enrichissement applique successivement 7 couches d'information sur les IOC/CVE extraits. Chaque étape est indépendante et idempotente grâce à des flags de tracking par IOC.

1
VirusTotal — url, domaine, hash, ip → vt_malicious_count
2
AbuseIPDB — ip uniquement → abuseConfidenceScore, totalReports
3
URLScan.io — url, domaine → risk_flag, typosquat, keywords
4
Géolocalisation — ip → countryCode, country (ip-api.com)
5
Enrichissement CVE — cves → cvss_score, epss, description NVD
6
NLP CVE — description CVE → vendors, products, versions (spaCy)
7
Classification + Reliability + Scoring — threat_type, risk_score, priority_score
1
VirusTotal — Réputation Multi-Moteurs
Script : enrichment/enrichment_vt/enrichir_virustotal.py
url domaine hash ip

VirusTotal interroge ~70 moteurs antivirus et services de réputation. Un seul résultat peut dire si un fichier, une URL ou une IP est malveillant selon 70 sources indépendantes.

Stratégie Local-First (Cache)

  • Étape 1 : cherche l'IOC dans virustotal_data.json local
  • Si trouvé : utilise les données locales — zéro appel API
  • Si absent : appelle l'API VirusTotal, stocke le résultat local
  • Limite Free Tier : 4 req/min → délai de 15s entre appels API
  • Flag idempotent : passer_par_virustotal = 1 sur l'IOC
Le cache local évite de re-requêter VT à chaque run. Un IOC déjà dans la base locale ne consomme jamais de quota API.

Même logique Local-First que VT

3
URLScan.io — Analyse Comportementale Web
Script : enrichment/enrichment_url/enrichir_exclusive_urlscan.py
url domaine

URLScan.io visite réellement la page web dans un navigateur headless (Chromium) et analyse son comportement : redirections, ressources chargées, scripts exécutés, ressemblance avec des pages légitimes.

Logique de soumission asynchrone

  • Soumission d'un scan : POST /api/v1/scan
  • Poll asynchrone : GET /api/v1/result/{uuid} (attente ~30s)
  • Cache local : urlscan_flags.json — évite re-scan si déjà connu
  • Implémentation asyncio pour paralléliser les scans
  • Filtre pré-scan : rejet des URLs avec extensions .exe, .dll, .zip...
URLScan ne peut scanner que des URLs web réelles (http/https). Les URLs de distribution de malware peuvent être offline ou bloquer les bots.

Détection du typosquatting

URLScan compare le domaine à une liste de marques connues (Microsoft, PayPal, Google...) et détecte les similarités visuelles (ex: micros0ft-login.tk vs microsoft.com) via distance d'édition et substitutions de caractères.

Enrichissement CVE — CVSS, EPSS, Description NVD
Script : enrichment/enrichment_cve/enrichir.py + cve_enrchisment.py
cves uniquement

Pour chaque CVE identifiée dans un record, ce module va chercher son score CVSS, sa description technique et son score EPSS (probabilité d'exploitation dans les 30 prochains jours).

Sources interrogées

  • NVD API : /cves/2.0?cveId=CVE-XXXX → CVSS v3.1/4.0 + description
  • FIRST EPSS API : api.first.org/graphql/epss?cve=CVE-...
  • Base locale NVD : vérifiée en premier pour éviter les appels API

Logique de priorité CVE dans le scoring

Les CVE suivent un chemin spécial dans calculate_priority() : le score additif IOC est ignoré, seuls CVSS et EPSS comptent.

# Branche vulnerability dans scorer.py cvss = record.attrs["cvss_score"] epss = record.attrs["epss"] if cvss >= 9.0 or epss >= 0.9 → CRITICAL elif cvss >= 7.0 → HIGH elif cvss >= 4.0 → MEDIUM else → LOW
Ex: CVE-2021-44228 (Log4Shell) → CVSS 10.0 → CRITICAL automatique
6
NLP CVE — Extraction sémantique des descriptions
Script : enrichment/enrichment_cve/nlp_enrichir.py
spaCy en_core_web_sm

Une fois les descriptions CVE récupérées, spaCy les analyse pour en extraire les entités nommées pertinentes : quel logiciel, quelle version, quel éditeur est affecté.

Entrée : description CVE (NVD)

"Apache Log4j2 2.0-beta9 through 2.15.0 (excluding security releases 2.12.2, 2.12.3, and 2.3.1) JNDI features... allow an attacker with log message control to execute arbitrary code loaded from LDAP..."

Entités extraites par spaCy NER

  • ORG → vendors : ex: "Apache", "Microsoft"
  • PRODUCT → products : ex: "Log4j2"
  • GPE → platforms : ex: "Linux", "Windows"
  • Regex → versions : "2.15.0", "v1.2", "2.x"

Sortie dans le record enrichi

# record["attributes"]["nlp_analysis"] { "vendors": ["Apache"], "products": ["Log4j2"], "versions": ["2.15.0", "2.0-beta9"], "platforms": [], "tlp": "TLP:CLEAR", "nlp_enriched_at": "2026-06-20..." } # ET dans chaque cve.ioc_enrichment { "nlp_extracted": { ← même structure copiée "vendors": ["Apache"], ... } }

Tracking NLP

  • Flag nlp_enrichment_cve.last_run dans le tracking source
  • Compte entities_extracted : nb records avec NLP
  • Idempotent : skip si nlp_analysis déjà présent dans le record
7
Classification + Reliability + MITRE + Scoring
Script : enrichment/classification/enrichir.py — orchestrateur des 4 sous-étapes
tous les records

Étape finale et la plus complexe. L'orchestrateur IntelligenceOrchestrator applique 4 sous-étapes séquentielles sur chaque record _enriched.json.

Sous-étape 7.1 — Classification

  • ThreatClassifier.infer_threat_type() → threat_type
  • Valeurs : malware / phishing / vulnerability / suspicious
  • Basé sur : nom de fichier source, tags, description, malware_family dans IOC
  • ThreatClassifier.classify_attack_type() → attack_type
  • Valeurs : Botnet, RAT, Stealer, Ransomware, Dropper, RCE, Credential...

Sous-étape 7.2 — Reliability

  • SourceReliability.apply_reliability_tag()
  • → source_confidence (50–100) injecté dans le record
  • → tag reliability:high/medium/low
  • → confidence_label : HIGH / MEDIUM / LOW / UNVERIFIED

Sous-étape 7.3 — MITRE ATT&CK

  • map_record(record) → technique_id, tactic
  • Mapping basé sur attack_type → technique MITRE
  • Ex: RAT → T1219 (Remote Access Software)
  • Ex: Ransomware → T1486 (Data Encrypted for Impact)

Sous-étape 7.4 — Scoring

  • calculate_priority(record, threat_type) → priority_score + soc_action
  • calculate_additive_risk(record) → risk_score_additive (0–100)
  • Score individuel par IOC : ioc["risk_score"] + ioc["soc_action"]

Flags d'idempotence — Évite le double-traitement

Pipeline Parallèle — Telegram Leak + LLM

Ce pipeline est entièrement séparé du pipeline IOC/CVE classique. Il surveille des canaux Telegram hacktivistes, télécharge les fichiers partagés, et soumet chaque message à un LLM génératif pour le qualifier comme fuite de données ou bruit politique. Deux appels LLM distincts avec des prompts différents.

Telethon MTProto LLM Génératif 5 Providers IA Override Heuristique Corrélation Quotidienne
Pipeline IOC/CVE (Classique)
  • Sources : APIs, feeds RSS, JSON publics
  • Extraction : Regex + spaCy (règles fixes)
  • Sortie : IOC structurés (IP, hash, URL, CVE)
  • Tracking : MongoDB
  • Enrichissement : VT, AbuseIPDB, CVE, Scoring
  • Usage : Blocage, détection signature
Pipeline Telegram Leak (Parallèle)
  • Sources : Canaux Telegram hacktivistes privés
  • Analyse : LLM génératif (prompt en langage naturel)
  • Sortie : Incidents de fuite (PII, DB, credentials)
  • Tracking : tracking.json local
  • Enrichissement : Corrélation LLM cross-messages
  • Usage : Alerte fuite, investigation, bulletin PDF

Téléchargement fichiers

  • Limite : 200 MB par fichier (flag SKIPPED_TOO_LARGE si dépassé)
  • Progress callback temps réel : XX.X MB / YY.Y MB (ZZ.Z%)
  • Archives ZIP/RAR extraites → listing des fichiers internes
  • Lecture 100 premières lignes de chaque .txt/.sql/.csv/.json/.log
  • Détection encodage BOM : UTF-8, UTF-16, UTF-32
  • Résultat tronqué à 6 000 chars → file_sample envoyé au LLM

Prompt LLM #1 — Texte complet envoyé

Analyze the following data leak message and associated file content.
Your task is to identify CORPORATE, BUSINESS, or GOVERNMENT data leaks.

CRITERIA:
1. IS A LEAK IF: Contains enterprise data, company employee lists, corporate credentials, business databases, PII from customers (Nom, Prénom, CIN, Téléphone, Adresse, etc.), or any structured data that looks like a database export.
2. SENSITIVITY: If a file sample is provided, be EXTRA SENSITIVE. If you see emails, names, numbers, or structured lines, mark it as a leak (is_leak: true).
3. IS NOT A LEAK IF: Purely political news, religious content, public propaganda, general chat, or generic system messages WITHOUT any attached files or data patterns.

SPECIAL INSTRUCTIONS:
— FILE CONTENT IS KEY: Even if the Telegram message is vague, if the 'File Sample' contains structured data (CSVs, logs, SQL), it IS A LEAK.
— POLITICAL FILTER: If the message contains political rhetoric BUT also includes a database or credentials, IT IS A LEAK. Focus the summary on the DATA.
— OUTPUT: Respond ONLY in valid JSON format with these keys:

{
  "is_leak": boolean,
  "severity": "low|medium|high|critical",
  "leak_type": "Database|Credentials|PII|Corporate_Secret|Other",
  "summary": "Short summary in French (max 2 sentences), focusing strictly on the exfiltrated data.",
  "targets": ["Company or Organization name"],
  "confidence": number
}

Message text: {text[:1500]}
File Sample: {file_context[:1000]}

4
Override Heuristique — Protection contre les Faux Négatifs LLM
process_message() dans core/collector.py
archives = leaks confirmées

Le LLM analyse le texte Telegram — souvent en arabe, avec rhétorique politique — et peut conclure à tort que ce n'est pas une fuite. Mais si un .zip de 200 MB est attaché, c'est quasi-certainement une fuite réelle. L'override corrige ce biais.

Logique dans le code

# Extensions qui déclenchent l'override ARCHIVE_EXTS = ( '.zip', '.ziip', '.rar', '.dbf', '.sql', '.xlsx', '.xls', '.xlsm', '.csv', '.txt', '.log' ) is_archive = file_path.endswith(ARCHIVE_EXTS) # Si LLM dit non MAIS fichier archive présent if is_archive and not analysis["is_leak"]: analysis["is_leak"] = True analysis["title"] = "Database Dump / Archive Leak" analysis["severity"] = "High" # → record QUAND MÊME sauvegardé

Tableau de décision

LLM ditArchive ?Action finale
is_leak = falseNonSkip — non sauvegardé
is_leak = falseOuiOverride → sauvegardé
is_leak = trueN'importeSauvegardé normalement
Résultat regex : En parallèle du LLM, extract_patterns() extrait toujours emails, IPs, URLs, credentials par regex. Ces patterns peuplent analysis["entities"] même si le LLM est absent.
Remarque : Les fichiers supprimés physiquement (code commenté) sont gardés sur disque pour éviter les faux négatifs. Le commentaire [MODIFICATION PFE] dans le code le confirme explicitement.
5
IntelligenceAgent — Sauvegarde Purifiée
core/intelligence.py — save_intel()
leaks_intel.json

save_intel() ne stocke que les leaks confirmées avec fichier joint. Les messages-menaces textuels purs sont exclus ici — ils seront intégrés lors de la corrélation LLM #2.

Règles de filtrage à la sauvegarde

  • Skip si is_leak = false (double sécurité post-override)
  • Skip si extracted_files vide — preuve fichier obligatoire
  • ID unique : INTEL-{YYYYMMDD}-{ORG[:3]}-{msg_id}
  • Déduplication par intel_id — merge des fichiers si doublon
  • Deux destinations : data/leaks/{canal}/{date}/leaks.json + results/leaks_intel.json

Format INTEL sauvegardé

PROMPT LLM #2 — Corrélation & Fusion des Incidents du Jour
IntelligenceAgent.process_daily_leaks() · lancé par runner_intelligence.py
Corrélation cross-messages

Ce deuxième appel LLM ne s'exécute PAS en temps réel. Il est lancé manuellement (ou en tâche planifiée) sur l'ensemble des leaks collectés dans une journée pour un canal. Son rôle : fusionner une menace textuelle et l'archive correspondante en un seul incident consolidé.

Le problème que ça résout

📢 Message 51 — Menace textuelle
"سنكشف قاعدة بيانات وزارة الداخلية المغربية"
"Nous allons publier la BDD du Ministère de l'Intérieur"
→ save_intel() l'a ignoré : pas de fichier
📦 Message 53 — Archive publiée
"وزارة الداخلية.zip (2.3 GB)"
Archive avec 800k lignes d'employés
→ save_intel() l'a sauvegardé normalement
LLM #2 → fusionne 51+53 → un seul incident "Ministère de l'Intérieur" avec fichier + résumé unifié

4. Normalize the target names (e.g., 'CNOPS' and 'CNOPS', 'Ministère de l'Intérieur' and 'وزارة الداخلية' are the same).
