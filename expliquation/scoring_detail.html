1 Confiance Source — source_confidence

Avant tout calcul de risque, chaque source CTI reçoit un score de confiance fixe (0–100) défini dans reliability.py → SourceReliability.SOURCE_RELIABILITY. Ce score reflète la rigueur éditoriale, le taux de faux positifs connu et la réputation de la source.

Cas ThreatFox spécial : ThreatFox fournit une confiance native par IOC (ioc_enrichment.confidence). Le scoring utilise alors base_conf = max(source_confidence, tf_conf), ce qui permet à un IOC très confirmé d'avoir une base plus haute que la moyenne de la source.

Logique de mapping

# reliability.py — apply_reliability_tag() conf = get_confidence(source_name) # lookup ou partial-match if conf >= 90 → tag = "reliability:high" elif conf >= 75 → tag = "reliability:medium" else → tag = "reliability:low" record["source_confidence"] = conf # injecté dans le record JSON

2 Score de Risque par Type d'IOC — calculate_ioc_risk()

Le cœur du moteur : chaque IOC est scoré individuellement (0–100) selon son type. Les formules sont différentes pour les hash, les IP et les URL/domaines car les signaux disponibles varient.

HASH Types : sha256 / sha1 / md5 Sources : MalwareBazaar, ThreatFox, DFIR

Pour les fichiers malveillants, la formule distingue deux chemins selon la présence de téléchargements (intel_downloads) qui indique MalwareBazaar.

Chemin A — MalwareBazaar (intel_downloads > 0)

# Budget total : 40 + 40 + 20 = 100 # 1. Confiance source (40%) score += (base_conf / 100) * 40.0 # 2. VirusTotal (40%) — progressif sur 50 moteurs if vt > 0: score += 20.0 + min(20.0, ((vt-1)/49.0) * 20.0) # → vt=1 : +20.0 | vt=25 : +30.2 | vt=50 : +40.0 # 3. Volumétrie downloads (20%) if dl >= 500 → score += 20 elif dl >= 100 → score += 15 elif dl >= 10 → score += 10 else → score += 5

Chemin B — Autres sources ThreatFox / DFIR

# Budget total : 40 + 60 = 100 # 1. Confiance source (40%) score += (base_conf / 100) * 40.0 # 2. VirusTotal (60%) — progressif sur 50 moteurs if vt > 0: score += 30.0 + min(30.0, ((vt-1)/49.0) * 30.0) # → vt=1 : +30.0 | vt=25 : +45.3 | vt=50 : +60.0 # (pas de signal intel_downloads)

Fallback — Types non reconnus

Pour tout IOC de type inconnu (ex: email, certificate), la formule simplifie à deux composantes :

# Fallback — type non reconnu score = (base_conf / 100) * 50.0 # 50% confiance source if vt > 0: score += 25.0 + min(25.0, ((vt-1)/49.0) * 25.0) # 50% VT

3 Pénalité Faux Positifs & Score Global

Pénalité faux positifs (×0.25) :
Si vt_malicious_count == 0 ET vt_harmless_count > 20, le score est divisé par 4.
Cas typique : URLs Malpedia ou ressources légitimes passant dans un feed. Un score de 30 devient 7.5.
# Appliqué APRÈS tous les calculs, AVANT le min(100) vt_harmless = e.get("vt_harmless_count", 0) if vt == 0 and vt_harmless > 20: score = score * 0.25 # ex: 30 → 7.5 (plus dans la zone MEDIUM) return round(min(100.0, score), 1)

Agrégation du score global : règle du maximum

Un record peut contenir plusieurs IOCs de types différents (ex: une IP C2 + un hash de payload + une URL de distribution). Le score de risque global du record est le maximum des scores IOC individuels — pas une moyenne.

# calculate_additive_risk() — score global 0-100 source_conf = record.get("source_confidence", 50) iocs = record.get("iocs", []) if not iocs: return round(min(100.0, source_conf * 0.5), 1) # fallback sans IOC scores = [calculate_ioc_risk(ioc, source_conf) for ioc in iocs] return max(scores) # ← règle du maximum : l'IOC le plus risqué détermine le record
Pourquoi le maximum et pas la moyenne ?
Un seul IOC confirmé malveillant suffit à classer une campagne. Une moyenne diluerait le signal : si un record a un hash à 90 et deux URLs bénignes à 10, la moyenne (37) cacherait la menace réelle.

Score individuel par IOC — stocké dans le record

# enrichir.py — après calculate_additive_risk src_conf = record.get("source_confidence", 50) for ioc in record["iocs"]: ioc["risk_score"] = calculate_ioc_risk(ioc, src_conf) # Action SOC au niveau IOC if ioc["risk_score"] >= 70 → ioc["soc_action"] = "investigate" elif ioc["risk_score"] >= 40 → ioc["soc_action"] = "monitor" else → ioc["soc_action"] = "monitor_quiet"

Cas des vulnérabilités — CVSS prime

Pour les records de type threat_type = "vulnerability", le score additif est ignoré. La priorité dépend directement du CVSS et de l'EPSS :

5 Pipeline Complet — enrichir.py

L'orchestrateur IntelligenceOrchestrator.run() applique les 4 étapes dans l'ordre sur chaque record JSON enrichi :

1. Classification — ThreatClassifier.infer_threat_type()
→ malware | phishing | vulnerability | suspicious
2. Fiabilité — SourceReliability.apply_reliability_tag()
→ source_confidence + reliability:high/medium/low
2.5 MITRE ATT&CK — map_record()
→ technique_id, tactic (optionnel)
3. Scoring — PriorityScorer.calculate_priority()
→ priority_score + soc_action + risk_score_additive
4. Marquage — tag soc_enriched
→ évite le double-traitement (idempotent)

Champs produits dans le JSON final

{ // Ajoutés par Classification "threat_type": "malware", "attack_type": "RAT", // Ajoutés par Reliability "source_confidence": 90, "confidence_label": "HIGH", "tags": ["reliability:high", "soc_enriched"], // Ajoutés par MITRE "technique_id": "T1071.001", "tactic": "command-and-control", // Ajoutés par Scoring "priority_score": "CRITICAL", "soc_action": "escalate", "risk_score_additive": 87.3, // Ajouté par IOC individuel "iocs": [{ "type": "ip", "value": "185.x.x.x", "risk_score": 87.3, "soc_action": "investigate" }] }
Idempotence : Les flags passer_par_callasifcation, paser_reliablity, passser_par_scoring évitent le recalcul si le script est relancé. L'option --skip-enriched ajoute un deuxième filtre sur le tag soc_enriched.

Exemple 5 — Record multi-IOC (IP C2 + Hash payload) CRITICAL via max()

Un seul record ThreatFox contient deux IOCs : une IP C2 à risque moyen et un hash très détecté.

IOC #1 — IP (C2)
vt=5, abuse=40, no online score IP = (90/100)×30 + (15+1.63) + (40/100)×30 = 27 + 16.63 + 12 = 55.6
MEDIUM 55.6 soc_action: monitor
IOC #2 — SHA256 (payload)
vt=45, no dl → chemin B score = (90/100)×40 + 30+min(30,(44/49)×30) = 36 + 30+26.94 = 92.9
CRITICAL 92.9 soc_action: investigate
risk_score_additive = max(55.6, 92.9) = 92.9
Priorité record = CRITICAL / soc_action = escalate
Le hash très détecté fait monter tout le record en CRITICAL, même si l'IP seule serait MEDIUM.

VT progressif — formule générique

# Garantit un minimum (floor) à la première détection # puis monte vers le max sur 50 moteurs VT_score = floor + min(cap, ((vt-1) / 49.0) × cap) # Hash (autres) → floor=30, cap=30 → range [30..60] # Hash (MB) → floor=20, cap=20 → range [20..40] # IP / URL → floor=15, cap=15 → range [15..30] # Fallback → floor=25, cap=25 → range [25..50] # vt=1 → floor + 0 (minimum garanti) # vt=25 → floor + cap×0.49 (mi-chemin) # vt=50 → floor + cap (maximum)
