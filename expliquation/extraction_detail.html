Classe BaseExtractor — Rôle

La classe BaseExtractor est le moteur commun à tous les extracteurs sources. Elle fournit :

  • Les patterns regex pour chaque type d'IOC
  • La whitelist de domaines bénins (google.com, github.com...)
  • La logique d'extraction et déduplication
  • L'ancrage des attributs source dans chaque IOC
  • Le merge des records existants vs nouveaux
Chaque source hérite de BaseExtractor ou l'instancie directement. Les extracteurs spécifiques (ex: dfir_report_extractor.py) ajoutent leur propre logique de filtrage en plus.

Regex d'Extraction par Type d'IOC

TypePrioritéPattern RegexNormalisationCas spéciaux
CVE 1 (premier) CVE-\d{4}-\d{4,} .upper() Dédupliqué par cve.id
URL 2 (haute) \bhttps?://[^\s<">]+\b .strip() Blacklist phishtank.com/phish_detail... — Whitelist domaine hôte
Email 3 [a-zA-Z0-9._%+-]+@[...]+\.[a-zA-Z]{2,} .lower() Type autr dans le JSON de sortie
SHA256 4 [a-fA-F0-9]{64} .lower() Mapping hash → nom de fichier via extract_file_hashes_general()
SHA1 4 [a-fA-F0-9]{40} .lower() Type hashe unifié
MD5 4 [a-fA-F0-9]{32} .lower() Type hashe unifié
IP/CIDR 5a \d{1,3}\.\d{1,3}..../\d{1,2} via ipaddress.ip_address() Ranges extraits EN PREMIER, évite duplication dans IPs simples
IP:Port 5b \d{1,3}\.\d{1,3}...:\d{1,5} gardé tel quel Extrait avant IPs simples pour éviter collision
IP simple 5c (?:(?:25[0-5]|2[0-4]\d|...)\.){3}... ipaddress.ip_address() Skip si déjà inclus dans un IP:Port ou CIDR
Domaine 6 (dernier) (?:[a-z0-9][a-z0-9-]{0,61}\.)+[a-z]{2,} .lower() Skip si : dans une URL déjà extraite, extension fichier, whitelist, pas de point

Ordre de priorité — pourquoi ?

L'ordre évite les collisions : une URL http://evil.com est extraite comme URL, et son domaine evil.com n'est PAS re-extrait séparément (test val_lower in ioc['value'].lower()). Idem pour IP:port avant IP simple.

Mapping Hash → Nom de Fichier

extract_file_hashes_general() parcourt le texte pour associer chaque hash à son nom de fichier. 4 formats supportés :

FormatExemple
Header blockFile: w.exe puis a3f2...hash
Inline separatorw.exe: a3f2... ou w.exe - a3f2...
Inline parenthèsesw.exe (a3f2...)
Checksum utilitya3f2... *w.exe

Résultat dans le JSON

# Champ "file" ajouté à l'IOC hash { "type": "hashe", "value": "a3f2c7...9d1e", "file": "w.exe", ← ajouté si trouvé "source": "DFIR Report", "ioc_enrichment": {} }
Les fichiers .conf, .log, .xml, .json sont exclus du mapping — seuls les exécutables et scripts sont mappés.

NLP spaCy — Utilisé UNIQUEMENT pour DFIR Report

🧠 spaCy en_core_web_sm — Contexte sémantique des rapports DFIR

Le NLP est activé à deux endroits dans la plateforme, toujours dans le contexte DFIR Report : (1) dans l'extracteur pour filtrer les faux positifs et contextualiser les IOC, (2) dans l'enrichissement NLP CVE pour extraire entités de la description CVE.

Contexte 1 — Extracteur DFIR

Fonction : _extract_nlp_context(text) dans dfir_report_extractor.py

  • Nettoyage HTML : suppression balises <script>, <style>, attributs WordPress
  • Analyse du texte nettoyé (max 100 000 chars) par spaCy NER
  • Classification des entités en 5 catégories
  • Extraction regex complémentaire : versions logicielles et commandes système
actor
Groupes d'attaquants
label ORG + keywords (spider, apt, lockbit...)
victim
Cibles / infrastructures
labels GPE, LOC, ORG non-acteur
command
Outils & commandes
regex cmd.exe, powershell, whoami + .exe/.dll/.ps1
technology
Logiciels & versions
label PRODUCT + regex "nom v1.2.3"
other
Entités contextuelles
tout le reste non classifié

Contexte 2 — Enrichissement NLP CVE

Fonction : extract_entities(text) dans enrichment/enrichment_cve/nlp_enrichir.py

  • Appliqué aux descriptions CVE des records enrichis (output_enrichment/)
  • Extrait : vendors (ORG), products (PRODUCT), platforms (GPE), versions (regex)
  • Ajouté dans record["attributes"]["nlp_analysis"]
  • Propagé aussi dans chaque cve["ioc_enrichment"]["nlp_extracted"]
# Résultat dans output_enrichment/nvd_enriched.json record["attributes"]["nlp_analysis"] = { "vendors": ["Apache", "Microsoft"], "products": ["Log4j", "Windows Server"], "versions": ["2.14.1", "v2.0"], "platforms": ["Linux"], "tlp": "TLP:CLEAR", "nlp_enriched_at": "2026-06-20T..." }

Filtrage faux positifs par NLP — Interaction avec l'extraction

Les entités NLP extraites servent de contexte dynamique pour filtrer les faux positifs dans _is_false_positive() :

# Logique de filtre dynamique NLP dans dfir_report_extractor.py legit_names = set() for key in ["victim", "command", "other"]: for item in nlp_analysis.get(key, []): cleaned = re.sub(r'[^a-z0-9]', '', item.lower()) legit_names.add(cleaned) # ex: "microsoft" "cmd" "powershell" # Lors du test d'un domaine extrait : sld = _get_sld(domain) # "microsoft" depuis "login.microsoft.com" if sld in legit_names: return True # → faux positif, nom d'outil mentionné dans le texte
Cette logique NLP est UNIQUE à DFIR Report. Aucun autre extracteur ne fait de NLP. Pour les autres sources (ThreatFox, FeodoTracker, MalwareBazaar...), les IOC sont déjà structurés : pas besoin de NLP, les champs sont directement mappés.

Filtres Faux Positifs — BaseExtractor

Whitelist domaines bénins

Domaines toujours ignorés même s'ils apparaissent dans un texte malveillant :

google.com · microsoft.com · amazon.com · cloudflare.com
github.com · apple.com · facebook.com · openai.com
sinkhole.ch · abuse.ch · shadowserver.org
phishtank.com · abuseipdb.com · nist.gov · localhost
Extensions invalides — domaines

Valeurs qui ressemblent à des domaines mais sont en réalité des noms de fichiers :

.exe .dll .zip .rar .7z .tar .gz .bin .dat
.hta .msi .bat .vbs .scr .js .elf .sh .lnk
.conf .ini .cfg .xml .json .yaml .txt .log
Déduplication finale : après extraction, chaque IOC est dédupliqué par la clé (type, value). Puis le merge entre enregistrements existants et nouveaux se fait par record_id avec fusion des champs iocs, cves, tags, references et attributes.

Analyze the following data leak message and associated file content. Your task is to identify CORPORATE, BUSINESS, or GOVERNMENT data leaks. CRITERIA: 1. Message text: {text[:1500]} File Sample: {file_context[:1000]}

Parsing de la réponse LLM — _parse_ai_json()

Le LLM peut envoyer du JSON en bloc markdown (```json ... ```), du JSON brut, ou du texte avec JSON inséré. La fonction extrait robustement :

  • Cherche un bloc ```json...``` en premier (markdown)
  • Sinon : cherche le premier { et le dernier } dans la réponse
  • Parse json.loads() sur cette portion extraite
  • Si échec → retourne None → fallback sur l'analyse regex

Étape 4 — Override Heuristique : Protection contre les Faux Négatifs

Le LLM peut parfois marquer un message comme "non-fuite" si le texte Telegram est vague (ex: message en arabe sans contexte explicite). Mais si une archive est attachée, c'est presque toujours une fuite réelle. L'override heuristique corrige ce cas.

# Extension archives qui déclenchent l'override ARCHIVE_EXTS = ( '.zip', '.ziip', '.rar', '.dbf', '.sql', '.xlsx', '.xls', '.xlsm', '.csv', '.txt', '.log' ) # Logique override dans process_message() if file_path.endswith(ARCHIVE_EXTS): is_archive = True if is_archive and not analysis["is_leak"]: analysis["is_leak"] = True analysis["title"] = "Database Dump / Archive Leak" analysis["severity"] = "High" # → Le record est QUAND MÊME sauvegardé

Tableau de décision

LLM ditArchive présente ?Action
is_leak = falseNonSkip — record non sauvegardé
is_leak = falseOui (zip, csv...)Override → is_leak = true forcé
is_leak = trueN'importeSauvegardé normalement
Pourquoi cet override ? Les messages hacktivistes sont souvent en arabe avec du contexte politique. Le LLM les classe comme "propagande politique" (pas une fuite). Mais s'il y a un fichier .zip de 50 MB attaché, c'est clairement une fuite de données — peu importe le texte.
Regex en parallèle : Pendant l'analyse LLM, extract_patterns() extrait emails, IPs, URLs, credentials via regex. Ces patterns sont sauvegardés dans analysis["entities"] même si le LLM est indisponible.

Étape 5 — IntelligenceAgent : Sauvegarde Purifiée

save_intel() filtre et structure les enregistrements confirmés comme fuites. Il n'enregistre PAS les records sans fichier joint (règle métier) — les menaces textuelles pures sont intégrées lors de la corrélation.

  • Skip si is_leak = false — double vérification
  • Skip si aucun fichier attaché (extracted_files vide) — seules les fuites avec preuve sont sauvegardées
  • ID unique : INTEL-{YYYYMMDD}-{ORG3CHARS}-{msg_id}
  • Sauvegarde dans results/leaks_intel.json
  • Déduplication par intel_id avec merge si déjà présent

Format INTEL sauvegardé

{ "intel_id": "INTEL-20260408-CNO-51", "timestamp": "2026-04-08T10:23:00", "leak_date": "2026-04-08", "source_channel": "Jabaroot DZ", "leak_metadata": { "target_organization": ["CNOPS"], "leak_type": "Database", "severity": "high", "confidence_score": 95 }, "extracted_data": { ← Regex "emails": ["xxx@cnops.ma"], "ips": [], "credentials": ["admin@cnops.ma:p@ss"] }, "extracted_files": ["Jabaroot_DZ/2026-04-08/cnops.zip"], "summary_fr": "Fuite de base de données CNOPS contenant ~120k dossiers patients (nom, CIN, adresse)." }

Étape 6 — PROMPT LLM #2 : Corrélation et Fusion Quotidienne

🔗 Prompt de corrélation — IntelligenceAgent.process_daily_leaks()

Ce deuxième appel LLM est lancé par runner_intelligence.py. Il regroupe tous les leaks du jour pour un canal et demande au LLM de les corréler — notamment fusionner une menace textuelle et l'archive correspondante en UN seul incident.

Contexte du problème

Dans les canaux hacktivistes, un acteur publie souvent :

Message 51 (texte seul)
"سنكشف قاعدة بيانات وزارة الداخلية المغربية"
"Nous allons publier la base de données du Ministère de l'Intérieur"
Message 53 (avec archive)
"وزارة الداخلية.zip (2.3 GB)"
Archive contenant 800k lignes d'employés
LLM #2 → fusionne 51 + 53 en un seul incident "Ministère de l'Intérieur"

Prompt complet de corrélation

CORRELATION AND MAPPING TASK: Here are the Telegram leaks detected on {date_str} for channel {channel_name}. Your task is to correlate and map these messages into FINAL Intelligence Incidents. RULES: 1. If a message is a threat (تهديد) and another message contains the actual file/archive for the SAME target organization, you MUST MERGE them into ONE single incident. 2. A final incident should ideally have an extracted file. 3. Normalize the target names (e.g., 'CNOPS' and 'CNOPS', 'Ministère de l'Intérieur' and 'وزارة الداخلية' are the same). 4. Provide a unified summary for merged incidents in French. DATA: {json.dumps(prompt_data)} OUTPUT FORMAT (Strict JSON ONLY): { "incidents": [{ "target_organization": ["Target"], "leak_type": "PII/Database/Credentials", "severity": "high", "summary_fr": "Résumé unifié...", "extracted_files": ["path1","path2"], "original_ids": [51, 53] }] }

Résultat — Incidents finaux dans leaks_intel.json

# Après fusion LLM des messages 51+53 : { "intel_id": "INTEL-20260408-MIN-51", "leak_metadata": { "target_organization": ["Ministère de l'Intérieur"], "leak_type": "Database", "severity": "high", "confidence_score": 1.0 ← 100% car fichier confirmé }, "extracted_files": ["Jabaroot_DZ/2026-04-08/wiz_interieur.zip"], "summary_fr": "Fuite massive de données du Ministère de l'Intérieur marocain : archive ZIP de 2.3 GB contenant ~800k dossiers d'employés (nom, prénom, CIN, adresse, grade)." }

Retry Automatique & Fallback Regex

Backoff exponentiel sur _query_ai()

max_retries = 3 backoff_factor = 2.0 for attempt in range(1, 4): try: response = LLM_call(prompt) return response except Exception: sleep_time = 2.0 ** attempt # Tentative 1 : sleep 2s # Tentative 2 : sleep 4s # Tentative 3 : sleep 8s → erreur finale await asyncio.sleep(sleep_time)

Fallback Regex si LLM indisponible

extract_patterns() s'exécute TOUJOURS, avant ou sans LLM :

PatternRegex
Emails[a-zA-Z0-9._%+-]+@...
IPs\b\d{1,3}\.\d{1,3}...\b
URLshttps?://[^\s<">]+
Credentialsemail@...:password
Si des entités regex sont trouvées → is_leak=true avec confidence=70 même sans LLM. Le champ summary indique "No AI analysis available".
